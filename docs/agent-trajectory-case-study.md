# 案例研究：決策軌跡與配對檢定如何否決一次上線

> **對應里程碑**：A0–A7（tool-calling agent 與 trajectory eval）
> **日期**：2026-08-18
> **一句話**：一套實作完整、單元測試 100% 覆蓋分支、通過所有安全門檻的
> tool-calling agent，最後的結論是**不要上線**。做出這個判斷的不是直覺，
> 是決策軌跡與 36 則案例的配對統計檢定。

---

## 1. 摘要

| 面向 | 資料 | 判定 |
| :--- | :--- | :--- |
| 幻覺率 | 0%（0/53，95% CI [0%, 6.8%]） | 通過 |
| fallback 率 | 0%（0/36，95% CI [0%, 9.6%]） | 通過 |
| 報價正確率 | 97.2% vs baseline 97.2% | 持平 |
| 欄位全對率 | 77.8% vs baseline 86.1%（配對差異 3:0） | 落後 |
| 客戶平均被問題數 | 1.58 vs baseline 1.50 | **與目標相反** |
| 每案成本 | $0.001259 vs $0.000447 | 2.8 倍 |
| 平均延遲 | 2730ms vs 1411ms | 1.9 倍 |

安全門檻全數通過，但沒有任何一項品質指標顯示 agent 較優，而導入它的原始理由
（讓客戶少答幾題）被資料直接否定。**結論是維持 feature flag 關閉。**

這份文件記錄的是達成這個結論的三個關鍵事件，以及它們的共同點。

---

## 2. 背景：這次的盲區與上一次不同

[上一份案例研究](eval-driven-fix-case-study.md)記錄的問題是「LLM 的**輸出品質**沒有量測」，
解法是建立 golden set。那個洞補起來之後，這次遇到的是另一類：

> **多步 agent 多出一種單步流程沒有的失效模式：結果對，但路徑荒謬。**

agent 可能繞了 7 步、重複查 3 次價目表、或在無效迴圈裡打轉，而最終欄位仍然
抽對。既有的 `cost_logs` 只記「呼叫了幾次 LLM、花了多少錢」，看不出「它為什麼
這樣走」。golden set 量的是終點，量不到路徑。

這是 `agent_steps` 這張表存在的理由，也是本文三個事件的共同前提。

---

## 3. 事件一：168 個綠燈測試，而 agent 從未運作過

### 發生了什麼

A4 完成時（commit `10b4ee6`），Python 側 **168 個單元測試全綠**，`mypy --strict`
乾淨，覆蓋率 94.8%，`app/agent/loop.py` 的 9 種終止路徑分支覆蓋率 100%。以任何
既有標準來看，這個模組都算完成了。

接著寫了一支對真實依賴執行的驗收腳本（`scripts/verify_agent.py`），首次執行，
兩個情境**都在第二步死於 `llm_error`**，軌跡停在 `lookup_rate_card` 之後。

真實錯誤是：

```
400 INVALID_ARGUMENT: Function call is missing a thought_signature in functionCall parts
```

### 根因

loop 原本的做法是拿 `tool_name` 與 `args` **自行重建**模型那一回合的內容，再放回
對話裡繼續下一輪。這在直覺上沒問題：資訊都在，重建一個等價的物件即可。

但 Gemini 3 的 `function_call` part 帶有 `thought_signature`，下一輪必須**原樣附回**。
重建出來的 part 沒有這個簽章，於是每一次 loop 都在第二步被 API 擋下。

**agent 從實作完成的那一刻起，就沒有真正運作過一次。**

### 為什麼 168 個測試沒有攔住

因為單元測試用的是假 LLM，而假 LLM 不驗簽章。測試驗證的是「拿到 function_call
之後 loop 的控制流程對不對」，那部分確實是對的。沒有驗證的是「真實 API 會不會
接受我們送回去的東西」。

這與上一份案例研究的教訓是同一句話的不同版本：**測試餵的是自己寫的乾淨資料時，
驗證的永遠只是「拿到值之後的邏輯」。**

### 修復

讓 `ToolTurnResult` 帶回模型這一回合的原始 `Content`，loop 直接把它放回去，
不再重建。

修復的**測試寫法**本身值得記錄。由於假 LLM 驗不了簽章，無法從「簽章對不對」
這個角度測試，改為斷言**物件身分**：

```python
# 送回 API 的必須是模型給的那一個物件，而不是內容相等的另一個
assert captured[1][1] is first.model_content
```

用 `is` 而非 `==`。這是在假依賴的限制下，唯一能把關「有沒有原樣傳遞」的角度。

另外，`model_content` 缺席時選擇交棒 fallback，而不是退回重建。捏出來的內容
會讓下一輪被擋下，而錯誤還會歸因到別的地方，比直接讓路更難查。

## 4. 事件二：軌跡看見了指標看不見的自我修正

### 一則被指標記為「異常」的案例

A6 全量執行後，trajectory 指標把 `web-007` 標記為「走出非期望路徑」：期望 3 步，
實際 4 步。

若只看指標，這是一則需要調查的退步。但軌跡把發生的事完整記了下來：

```
1. lookup_rate_card                                    ok
2. record_fields                                       ok
3. ask_customer  ← 一次丟出 7 題                        rejected
4. ask_customer  ← 改成 5 題                            ok  → loop 結束
```

`ask_customer` 有 `MAX_QUESTIONS_PER_ROUND = 5` 的檢查。模型一次想問 7 題，
被 tool 擋下；由於該檢查回傳的是 `rejected` 而非拋錯，**loop 不終止**，
把拒絕原因餵回對話，模型在同一趟 loop 裡自己改成 5 題並通過。

這不是缺陷，是**護欄生效後模型自行修正**。

### 為什麼只有軌跡看得見

兩側的最終產出完全相同：同樣的缺漏欄位判定、同樣的報價結果。在 11 項既有指標
上，這則案例與 baseline 沒有任何差異。它在指標上唯一的痕跡，就是「多了一步」
這個看起來像退步的數字。

**若沒有記錄軌跡，這件事的存在完全不可見。** 而它恰好是整個 tool 層設計最想
證明的東西：把約束放在 tool 的參數驗證裡，模型違反時會得到具體的錯誤訊息並
自行修正，不需要人介入。

### 影響到 UI 的設計

這則案例直接決定了 A7 軌跡介面的一個措辭選擇：`rejected` 狀態顯示為
「參數不合規，已重試」而非「失敗」，用提醒色而非錯誤色，且不列入該趟 loop 的
去向判定。

把護欄生效顯示成失敗，會讓正常行為在商家眼中看起來像故障。A7 的 E2E 種入的
測試資料就是照 `web-007` 的形狀寫的。

## 5. 事件三：資料否決了功能本身

### 為什麼用配對檢定

A6 要回答「agent 比單步流程好嗎」。兩側跑的是**同一批** 36 則 golden case，
不是兩組獨立抽樣，因此正確的檢定是 **McNemar 精確檢定**而非卡方獨立性檢定
（後者假設兩組互不相關，會高估顯著性）。

配對檢定只看兩側**表現不同**的案例，把「這則案例本身很難」這個共有變異消掉。

### 結果

| 判準 | baseline | agent | 配對差異 | McNemar p |
| :--- | :--- | :--- | :--- | ---: |
| `quote_correct` | 97.2% | 97.2% | 0 : 0 | 1.0000 |
| `fields_all_correct` | 86.1% | 77.8% | 3 : 0 | 0.2500 |
| `clarification_exact` | 97.2% | 88.9% | 3 : 0 | 0.2500 |

三個判準中兩個落後，無一領先，且不一致的案例**全部指向同一個方向**。

### p = 0.25 不代表「一樣好」

不一致的案例只有 3 則。在「兩者無差異」的虛無假設下，3 則全倒向一邊的機率是
0.25，還不到能下結論的程度。

檢定力分析說得更直接：**以 97.2% 為基準、要偵測 5pp 的退步，每組需要 313 則；
本次只有 36 則。** 所以「不顯著」在這裡的意思是「看不出來」，不是「沒有差異」。

這一點刻意寫進報告，是因為「小樣本沒有顯著差異」被讀成「兩者一樣好」是統計上
最常見的誤讀。

### 壓垮結論的是原始動機

導入 agent 的產品面理由是「客戶少答幾題」。這一項獨立量測：

| | 平均被問欄位數 | 總題數 |
| :--- | ---: | ---: |
| 標註（正確答案） | 1.47 | 53 |
| baseline | 1.50 | 54 |
| **agent** | **1.58** | **57** |

agent 問得**更多**。唯一的產品面理由沒有成立。

### 回歸的根因是單一的

三則回歸案例全部是同一個缺陷：agent 沒有抽出以「一款」「一組」寫成的數量。

| 案例 | 原文片段 | 標註 | baseline | agent |
| :--- | :--- | :--- | :--- | :--- |
| `graphic-006` | 需要**一款**LOGO | 1 | 1 | null |
| `graphic-010` | 設計**一款**LOGO | 1 | 1 | null |
| `illu-008` | 貼圖表情包**一組** | 1 | 1 | null |

值得注意的是**後果比看起來輕**：金額沒有受影響，因為計價層在 quantity 缺值時
以 1 計算，故 `quote_correct` 兩側打平。實際代價就是上面多出來的那 3 題。

這個缺陷其實在 WBS 6.8 的備註裡早有記錄，當時的評估是「不影響當前計價，
只會多問一題」。A6 證實了那個評估完全正確，只是 agent 側多犯了兩則，
使它從「已知的小瑕疵」變成「配對比較上的可見退步」。

## 6. 三個事件的共同點

| 事件 | 既有防線的狀態 | 抓到它的是什麼 |
| :--- | :--- | :--- |
| agent 從未運作過 | 168 單元測試全綠、分支覆蓋率 100% | 對真實依賴執行的驗收腳本 |
| 護欄自我修正 | 11 項指標無差異 | 決策軌跡 |
| 功能不該上線 | 所有安全門檻通過 | 36 則案例的配對檢定 |

三者的共同結構是：**綠燈的防線都在正確地驗證它們負責的東西，問題出在它們負責
的範圍之外。**

- 單元測試負責控制流程，不負責真實 API 的契約
- 指標負責結果品質，不負責路徑
- 安全門檻負責「有沒有危險」，不負責「有沒有價值」

每加一層新的抽象（單次呼叫 → 多步 agent），就會多出一塊既有防線照不到的區域。
那塊區域需要新的量測，而不是把既有的量測跑更多次。

---

## 7. 這個案例證明了什麼

**先量測，再開啟。** 如果當初直接把 flag 打開上線，那三則欄位退步與多出來的
提問不會有任何人發現，因為報價金額是對的，端到端流程也是通的。它會表現為
「客戶偶爾多被問一題」，而那永遠不會被歸因到某次架構變更。

**觀測性要在需要它之前就建好。** `agent_steps` 是在 A1 建的，比 agent 真正
能跑還早三個里程碑。事件二的自我修正若沒有那張表，就只是指標上一個無法解釋的
「多了一步」。

**願意用資料否定自己的產出。** A6 的結論對這個專案是不利的：投入數個里程碑實作
的功能，量測結果是不該上線。但把不利的數字寫進報告、寫進 README、維持 flag
關閉，比宣稱一個沒有根據的改善有價值得多。

設計文件在動工前就誠實寫過：

> 這次改動讓系統變慢、變貴、部署變複雜……**純產品 ROI 是負的**。真正的動機是
> 開發者熟悉度與職涯定位。

A6 的資料證實了這個事前判斷，而且比預期更不利。**技術實作的價值不因此消失**
（tool 層護欄、軌跡可觀測性、配對檢定的方法論都是真的），但它們的價值在於
過程本身，不在於一個不該上線的功能。
