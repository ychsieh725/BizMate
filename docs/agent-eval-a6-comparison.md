**執行日期**：2026-08-17
**資料集**：golden set v1.0.0，36 則（graphic_design / illustration / web 三類）
**模型**：兩側同為 `gemini-3.1-flash-lite`
**原始資料**：[`eval-artifacts/`](../eval-artifacts/)（逐案例結果，可自行重算）

重現方式：

```bash

pnpm eval --out=eval-artifacts/a6-baseline.json
cd agent-service && uv run python -m eval.runner --out ../eval-artifacts/a6-agent.json
uv run python -m eval.compare ../eval-artifacts/a6-baseline.json ../eval-artifacts/a6-agent.json
```

## 結論

**硬門檻通過，但沒有量到任何好處，且成本與延遲明顯上升。**

| 判定 | 結果 |
| :--- | :--- |
| 設計文件的 A6 閘門（幻覺率 0%、fallback 率 0%） | ✅ **通過** → A7 解除封鎖 |
| agent 品質優於 baseline | ❌ **未成立**——三個判準中兩個落後，無一領先 |
| 建議是否於 A8 開啟 flag | ❌ **不建議**，理由見〈為什麼不開 flag〉 |

閘門通過與「應該開啟」是兩件事。閘門問的是「有沒有危險」，這題答案是沒有；
但「有沒有價值」這題，資料的答案是**目前沒有**。

## 硬門檻

設計文件定義：幻覺率非 0 即不得開 flag；fallback 率非 0 代表 agent 這條路沒走完。

| 門檻 | 實測 | 95% CI | 判定 |
| :--- | ---: | :--- | :--- |
| 幻覺率 | **0.0%** (0/53) | [0.0%, 6.8%] | ✅ |
| fallback 率 | **0.0%** (0/36) | [0.0%, 9.6%] | ✅ |

36 則全部走完 agent loop，沒有一則退回既有路徑；53 個「原文未提及」的欄位，
沒有一個被杜撰出值。

> 區間上界要一起看。0/36 的 95% 上界是 9.6%——**這份資料無法排除真實 fallback
> 率高達 9.6% 的可能**。「實測 0%」不等於「不會發生」。

## 配對比較

兩側跑的是同一批案例，故用 McNemar 精確檢定而非卡方獨立性檢定。

| 判準 | baseline | agent | 配對差異 | McNemar p |
| :--- | :--- | :--- | :--- | ---: |
| `quote_correct` | 97.2% [85.8%, 99.5%] | 97.2% [85.8%, 99.5%] | 0 : 0 | 1.0000 |
| `fields_all_correct` | **86.1%** [71.3%, 93.9%] | 77.8% [61.9%, 88.3%] | **3 : 0** | 0.2500 |
| `clarification_exact` | **97.2%** [85.8%, 99.5%] | 88.9% [74.7%, 95.6%] | **3 : 0** | 0.2500 |

「配對差異」讀作「baseline 獨對 : agent 獨對」。

三個判準的定義：

- `quote_correct` — 報價與標註一致。**標註本身即無法計價時，轉人工才算對**；
  硬出一個數字反而是錯的（客戶拿到沒有根據的金額，比拿不到傷害更大）
- `fields_all_correct` — 所有欄位抽取正確（含正確判為 null）
- `clarification_exact` — 判定的缺漏欄位與標註完全相同（以集合比對，
  問題順序不代表品質）

### p = 0.25 不代表「兩者一樣好」

不一致的案例只有 3 則，而且**全部指向同一個方向**（baseline 3 : agent 0）。
在「兩者無差異」的虛無假設下，3 則全倒向一邊的機率是 0.25——樣本太小，
還不到統計上能下結論的程度。

檢定力分析說得更直接：**以 97.2% 為基準、要偵測 5pp 的退步，每組需要 313 則；
本次只有 36 則。** 所以「不顯著」在這裡的意思是「看不出來」，不是「沒有差異」。

## 專案原始動機的驗證

設計文件的動機是「客戶少答幾題」。這一項獨立量測：

| | 平均被問欄位數 | 總題數 | 完全不需追問 |
| :--- | ---: | ---: | ---: |
| 標註（正確答案） | 1.47 | 53 | — |
| baseline | 1.50 | 54 | 17 / 36 |
| **agent** | **1.58** | **57** | 16 / 36 |

**agent 問得比 baseline 多。** 這推翻了導入 agent 的原始理由。

（設計文件〈待確認事項〉#3 要求在 A6 補測 baseline 側，此表一併回答。）

## 品質回歸的根因：只有一個

三則回歸案例（`graphic-006`、`graphic-010`、`illu-008`）**全部是同一個缺陷**：

> agent 沒有抽出以「一款」「一組」寫成的數量。

| 案例 | 原文片段 | 標註 | baseline | agent |
| :--- | :--- | :--- | :--- | :--- |
| `graphic-006` | 需要**一款**LOGO | 1 | 1 ✅ | null ❌ |
| `graphic-010` | 設計**一款**LOGO | 1 | 1 ✅ | null ❌ |
| `illu-008` | 貼圖表情包**一組** | 1 | 1 ✅ | null ❌ |

全體來看，baseline 有 2 則數量抽錯，agent 有 5 則。

**這不是 prompt 規則的差異。** 兩側的抽取規則逐條比對後幾乎相同，都沒有
「未提及即預設 1」這種條款——事實上這三則原文都**明寫了**數量，是 agent 漏抽。

### 後果比看起來輕

金額**沒有受影響**：TypeScript 計價層在 quantity 缺值時以 1 計算，所以
`quote_correct` 兩側打平（0 : 0）。實際代價是**多問客戶一題**，也正是
上一節那 3 題的來源。

這也順帶解釋了 2 則軌跡偏離（`graphic-003`、`graphic-010`）——agent 以為
數量還沒抽到，於是呼叫 `ask_customer` 而非 `compute_quote`。

## 一則值得單獨記錄的軌跡

`web-007` 被計為「走出非期望路徑」（4 步而非 3 步），但看軌跡就知道那不是缺陷：

```
1. lookup_rate_card
2. record_fields
3. ask_customer  ← 一次丟出 7 題，超過單輪 5 題上限，被 tool 擋下
4. ask_customer  ← 模型改成 5 題，通過，loop 結束
```

`MAX_QUESTIONS_PER_ROUND = 5` 的檢查回傳 `rejected` 而非拋錯，故 loop 不終止、
把拒絕原因餵回對話，**模型在同一個 loop 裡自己修正了**。

這是 tool 層驗證與 loop 設計協同運作的實例，也說明為什麼終止類 tool 的
「被拒絕」與「成功」必須分開處理——若 `rejected` 也帶 event，客戶就會一次
收到 7 個問題。

而這件事**只有靠決策軌跡看得見**：兩側的最終產出完全相同，指標上也只表現為
「多了一步」。

## 為什麼不開 flag

| 面向 | 資料 |
| :--- | :--- |
| 安全性 | ✅ 幻覺 0、fallback 0、注入案例正常擋下 |
| 品質 | ⚠️ 三個判準中兩個落後，無一領先；差異方向一致（3 : 0） |
| 原始動機 | ❌ 客戶被問的題數**增加**（1.58 vs 1.50） |
| 成本 | ❌ 2.8× |
| 延遲 | ❌ 1.9× |

**沒有一項指標顯示 agent 比較好。** 在這種情況下開 flag，等於用 2.8 倍的成本
換一個量不出好處、且已知有品質退步的路徑。

### 建議的下一步

1. **修數量抽取缺陷** — 這是唯一的品質回歸根因，且集中在「數字＋量詞」的中文
   表達。修完重跑 A6，預期 `fields_all_correct` 與 `clarification_exact`
   兩項可回到與 baseline 持平
2. **重新檢視「少問幾題」是否為 agent 該負責的事** — baseline 的反問精準率
   已達 98.1%，距離標註只差 1 題。這個空間本來就小，agent 沒有發揮餘地
3. **擴充 golden set** — 36 則的檢定力不足以支撐任何「顯著改善」的宣稱。
   要證明 5pp 的差異需要每組 313 則

### 誠實的評估

設計文件〈風險與取捨〉早已寫明：

> 這次改動讓系統變慢、變貴、部署變複雜……**純產品 ROI 是負的**。真正的動機是
> 開發者熟悉度與職涯定位。

A6 的資料證實了這個判斷，而且比預期更不利——連「客戶少答幾題」這個唯一的
產品面理由都沒有成立。這不改變技術實作的價值（tool 層護欄、軌跡可觀測性、
配對檢定的方法論都是真的），但**它確實說明了「先量測再開啟」的必要性**：
若當初直接把 flag 打開上線，這些退步不會有任何人發現。
