# A6 基準線對照：tool-calling agent vs 單步流程

**資料集**：golden set v1.0.0，36 則（graphic_design / illustration / web 三類）
**模型**：兩側同為 `gemini-3.1-flash-lite`
**原始資料**：[`eval-artifacts/`](../eval-artifacts/)（兩次量測的逐案例結果，可自行重算）

本文件記錄兩次量測。第一次（2026-08-17）發現 agent 落後並找出根因；修復後
第二次（2026-08-18）重測，agent 追平 baseline。

重現方式：

```bash

pnpm eval --out=eval-artifacts/a6b-baseline.json
cd agent-service
uv run python -m eval.runner --out ../eval-artifacts/a6b-agent.json
uv run python -m eval.compare ../eval-artifacts/a6b-baseline.json ../eval-artifacts/a6b-agent.json
```

**硬門檻通過，agent 與 baseline 品質持平，但成本為 3 倍，仍不建議開啟 flag。**

| :--- | :--- |

## 第二次量測（2026-08-18，修復後）

### 配對比較

| 判準 | baseline | agent | 配對差異 | McNemar p |
| :--- | :--- | :--- | :--- | ---: |
| `quote_correct` | 100.0% [90.4%, 100%] | 100.0% [90.4%, 100%] | 0 : 0 | 1.0000 |
| `fields_all_correct` | 91.7% [78.2%, 97.1%] | 91.7% [78.2%, 97.1%] | 1 : 1 | 1.0000 |
| `clarification_exact` | 100.0% [90.4%, 100%] | 97.2% [85.8%, 99.5%] | 1 : 0 | 1.0000 |

「配對差異」讀作「baseline 獨對 : agent 獨對」。三個判準的定義：

- `quote_correct`：報價與標註一致。**標註本身即無法計價時，轉人工才算對**；
  硬出一個數字反而是錯的（客戶拿到沒有根據的金額，比拿不到傷害更大）
- `fields_all_correct`：所有欄位抽取正確，含正確判為 null
- `clarification_exact`：判定的缺漏欄位與標註完全相同。以集合比對，問題順序
  不代表品質

檢定方式為 **McNemar 精確檢定**：兩側跑的是同一批案例而非兩組獨立抽樣，
用卡方獨立性檢定會高估顯著性。配對檢定只看兩側表現不同的案例，把「這則案例
本身很難」這個共有變異消掉。

`fields_all_correct` 的 1:1 是本次唯一互有勝負之處，兩側各錯一則不同的案例。

### 硬門檻

| 門檻 | 實測 | 95% CI |
| :--- | ---: | :--- |
| 幻覺率 | **0.0%**（0/53） | [0.0%, 6.8%] |
| fallback 率 | **0.0%**（0/36） | [0.0%, 9.6%] |

36 則全部走完 agent loop，沒有一則退回既有路徑；53 個「原文未提及」的欄位
沒有一個被杜撰出值。

> 區間上界要一起看。0/36 的 95% 上界是 9.6%，**這份資料無法排除真實 fallback
> 率高達 9.6% 的可能**。「實測 0%」不等於「不會發生」。

### 客戶被問題數

| | 平均被問欄位數 | 總題數 |
| :--- | ---: | ---: |
| 標註（正確答案） | 1.47 | 53 |
| baseline | **1.47** | 53 |
| agent | 1.53 | 55 |

**baseline 現在與標註完全一致。** agent 仍多問 2 題。導入 agent 的產品面理由
（讓客戶少答幾題）依然沒有成立，而且 baseline 已經沒有可改善的空間。

### 成本

| | baseline | agent | 倍數 |
| :--- | ---: | ---: | ---: |
| 每案成本 | $0.000474 | $0.001443 | **3.0×** |

agent 平均 3.08 步，每步一次 Gemini 呼叫。

### 延遲：本次量測不可信

第二次量測的延遲數字大幅上升（agent 平均 10,080ms、P95 19,502ms，超過設計
文件的 10,000ms 門檻）。但**這個數字不能用來判斷**，理由如下。

同一批 8 則案例、同樣的程式碼、相隔約 20 分鐘的兩次執行：

| 案例 | 修復前 | 修復後（全量） | 重測 |
| :--- | ---: | ---: | ---: |
| `graphic-006` | 2,617ms | 17,503ms | 5,137ms |
| `graphic-007` | 2,614ms | 17,666ms | 4,725ms |
| 中位數 | 2,504ms | 8,828ms | 4,615ms |

**同樣的輸入，兩次量測差 2 倍。** 而每案成本（token 量的代理指標）只上升
7～15%，撐不起 1.8～3.7 倍的延遲差距。

結論：延遲的執行期變異遠大於本次改動的影響，單次全量執行不足以推論延遲。
要把 P95 當成閘門，必須先改為多次量測取中位數，這一項列為待辦。

## 第一次量測（2026-08-17）與它促成的修復

第一次量測的 agent 在三個判準中兩個落後、無一領先：

| 判準 | baseline | agent | 配對差異 | McNemar p |
| :--- | :--- | :--- | :--- | ---: |
| `quote_correct` | 97.2% | 97.2% | 0 : 0 | 1.0000 |
| `fields_all_correct` | 86.1% | 77.8% | **3 : 0** | 0.2500 |
| `clarification_exact` | 97.2% | 88.9% | **3 : 0** | 0.2500 |

不一致的案例只有 3 則，且全部指向同一個方向。p = 0.25 不代表「一樣好」：
檢定力分析顯示**以 97.2% 為基準、要偵測 5pp 的退步，每組需要 313 則**，
本次只有 36 則。所謂「不顯著」在這裡的意思是「看不出來」。

### 根因：計價單位從來沒有給模型

三則回歸案例全部是同一個缺陷，agent 沒有抽出以中文數量詞寫成的數量：

| 案例 | 原文片段 | 標註 | 第一次的 agent |
| :--- | :--- | :--- | :--- |
| `graphic-006` | 需要**一款**LOGO | 1 | null |
| `graphic-010` | 設計**一款**LOGO | 1 | null |
| `illu-008` | 貼圖表情包**一組** | 1 | null |

另有兩則**兩側都錯**：`illu-003`「一組貼圖，八款」被抽成 8，而該項目按組計價，
金額因此差 8 倍；`graphic-003`「一整套VI」被抽成 null。

解開這個歧義所需的資訊本來就在資料庫裡：`rate_card_base.unit` 記載
「貼圖表情包」的計價單位是「每組」。但兩側都只把 subtype 的**名稱清單**給模型，
沒有給單位。模型無從判斷「數量 1」代表什麼。

在 prompt 裡硬寫「貼圖＝每組」可以讓這一則過，但對其他商家不成立（有人真的
按款賣貼圖）。修法是把 `unit` 從資料帶出來，並在 prompt 說明數量是「幾個計價
單位」。

修復分兩輪：傳入計價單位後 5 則錯降為 1 則，`graphic-003`「一整套VI」仍失敗
（屬「數詞＋修飾字＋量詞」，與「一款」結構不同）；規則擴寫為「中文數量詞一律
換算，量詞前有修飾字也算」後降為 0 則。

### 修復對兩側都有效

| 指標 | baseline 修復前 | baseline 修復後 |
| :--- | ---: | ---: |
| 欄位抽取準確率 | 97.5% | **98.5%** |
| 反問精準率 | 98.1% | **100%** |
| 報價偏差（平均） | 22.6% | **0.0%** |
| 報價偏差（最大） | **700.0%** | **0.0%** |

那個 700% 就是 `illu-003` 的 8 倍錯價。

> 這個缺陷在 WBS 6.8 的備註裡早有記錄，當時評估為「不影響當前計價，只會多問
> 一題」。該評估對 `graphic-006` 一類是正確的，但漏看了 `illu-003`：它不是
> 「少抽一個值」，而是**抽到錯的值**，後果是 8 倍錯價而非多問一題。

## 一則值得單獨記錄的軌跡

`web-007` 被計為「走出非期望路徑」（4 步而非 3 步），但看軌跡就知道那不是缺陷：

```
1. lookup_rate_card
2. record_fields
3. ask_customer  ← 一次丟出 7 題，超過單輪 5 題上限，被 tool 擋下
4. ask_customer  ← 模型改成 5 題，通過，loop 結束
```

`MAX_QUESTIONS_PER_ROUND = 5` 的檢查回傳 `rejected` 而非拋錯，故 loop 不終止、
把拒絕原因餵回對話，**模型在同一個 loop 裡自己修正了**。

這是 tool 層驗證與 loop 設計協同運作的實例，也說明為什麼終止類 tool 的
「被拒絕」與「成功」必須分開處理，若 `rejected` 也帶 event，客戶就會一次
收到 7 個問題。

而這件事**只有靠決策軌跡看得見**：兩側的最終產出完全相同，指標上也只表現為
「多了一步」。

## 為什麼仍然不開 flag

| 面向 | 第一次量測 | 第二次量測（現況） |
| :--- | :--- | :--- |
| 安全性 | ✅ 幻覺 0、fallback 0 | ✅ 維持 |
| 品質 | ❌ 兩個判準落後（3 : 0） | ⚠️ **持平**，互有勝負（1 : 1） |
| 原始動機 | ❌ 1.58 vs 1.50 | ❌ 1.53 vs **1.47** |
| 成本 | ❌ 2.8× | ❌ **3.0×** |
| 延遲 | ❌ 1.9× | ⚠️ 量測不可信（見上） |

修復之後，「不該開」的理由從「它比較差」變成「**它沒有比較好**」。

決定性的一項是最後的產品理由：baseline 現在的反問數與標註**完全一致**
（1.47 = 1.47），沒有任何可改善的空間。agent 要贏，就得問得比正確答案還少，
那不是能力問題而是定義問題。**agent 在這個任務上沒有發揮餘地。**

在這種情況下開 flag，等於用 3 倍成本換一個結構上不可能出現的改善。

### 建議的下一步

1. ~~修數量抽取缺陷~~ → **已完成**（2026-08-18），兩側皆受益，`illu-003`
   的 8 倍錯價已消除
2. **把延遲改為多次量測取中位數** — 單次執行的變異達 2 倍，現行的 P95 門檻
   在這種量測品質下無法作為閘門
3. **擴充 golden set** — 36 則的檢定力不足以支撐任何「顯著改善」的宣稱。
   要證明 5pp 的差異需要每組 313 則
4. **若要讓 agent 有發揮空間，得換題目** — 目前的反問任務已被單步流程解到
   接近上限。agent 的價值應該在 baseline 做不到的地方尋找（例如需要跨輪推理
   或動態查詢的情境），而不是在一個已經解完的任務上比快

### 誠實的評估

設計文件〈風險與取捨〉在動工前就寫明：

> 這次改動讓系統變慢、變貴、部署變複雜……**純產品 ROI 是負的**。真正的動機是
> 開發者熟悉度與職涯定位。

兩次量測都證實了這個事前判斷。第一次的資料更不利（agent 明顯落後），修復後
收斂為持平，但結論不變。

值得記錄的是**修復本身的收益落在 baseline 身上**：`illu-003` 的 8 倍錯價是
兩側共有的缺陷，是 agent 側的配對比較把它推到不能忽視的位置，最後由單步流程
一併受益。用來評估 agent 的工具，產出的價值反而在別處。

這不改變技術實作的價值（tool 層護欄、軌跡可觀測性、配對檢定的方法論都是真的），
但它說明了「先量測再開啟」的必要性：若當初直接把 flag 打開上線，那些退步不會
有任何人發現，而 `illu-003` 的 8 倍錯價會繼續存在於兩條路徑上。
